# แผนกู้ระบบเมื่อข้อมูลเสียหาย (Disaster Recovery)

> เอกสารนี้อยู่ใน repo สาธารณะ — ห้ามใส่คีย์ อีเมล ชื่อลูกค้า หรือชื่อกิจการลงในนี้
> อัปเดต 5 ส.ค. 2569

## ตอนนี้เรามีเกราะกี่ชั้น

| ชั้น | ครอบคลุมอะไร | ไม่ครอบคลุมอะไร | ใครต้องทำ |
|---|---|---|---|
| **1. สำรองอัตโนมัติรายวัน** (`/api/cron/backup` → bucket `db-backups`) | migration พลาด · ลบผิด · ตารางเสีย · ข้อมูลถูกเขียนทับ | โปรเจกต์ Supabase หายทั้งก้อน (bucket อยู่โปรเจกต์เดียวกัน) | ตั้ง `CRON_SECRET` ครั้งเดียว |
| **2. สำรองลงเครื่องเจ้าของ** (`npm run backup`) | โปรเจกต์หายทั้งก้อน · บัญชีถูกระงับ | ช่วงเวลาตั้งแต่สำรองครั้งล่าสุดถึงตอนพัง | เจ้าของรันเอง + ก๊อปออกนอกเครื่อง |
| **3. Supabase Pro (PITR)** | ย้อนเวลาได้ระดับนาที ไม่ต้องพึ่งไฟล์ dump | — | **ยังไม่ได้เปิด** (~$25/เดือน) |

**ข้อสรุปที่ต้องรู้:** ชั้น 1+2 กู้ "ข้อมูล" ได้ แต่กู้ "ช่วงเวลาที่หายไประหว่างรอบสำรอง" ไม่ได้
เมื่อมีรายได้เข้าแล้วให้อัป Pro ทันที — นี่คือค่าใช้จ่ายก้อนแรกที่ควรจ่าย ไม่ใช่ก้อนสุดท้าย

## ตรวจว่าสำรองใช้ได้จริง (ทำเดือนละครั้ง)

```bash
npm run backup && npm run backup:verify
```

ตัวตรวจจะเทียบจำนวนแถวในไฟล์กับฐานจริงทีละตาราง และ **ตกทันที** ถ้าตารางแกนบัญชี
(`fin_docs` · `journal_lines` · `wallets` ฯลฯ) ว่างหรือหายไป
สำรองที่ไม่เคยตรวจ = ไม่ใช่สำรอง — ความล้มเหลวที่พบบ่อยที่สุดคือไฟล์มีจริงแต่ว่างเปล่า

## เมื่อเกิดเหตุจริง — ลำดับที่ต้องทำ

1. **หยุดเลือดก่อน** — ปิดการเขียนข้อมูลใหม่ (ตั้งประกาศปิดปรับปรุงที่หน้าแอดมิน)
   อย่าเพิ่งกู้ทับ ข้อมูลที่เขียนทับแล้วเอาคืนไม่ได้
2. **ประเมินขอบเขต** — เสียทั้งฐาน หรือเสียบางตาราง/บางแถว
   ดูจาก `accounting_integrity()` และเทียบกับไฟล์สำรองล่าสุด
3. **กู้จากชั้นที่ใกล้เวลาที่สุด** — Pro (ถ้าเปิดแล้ว) > bucket รายวัน > ไฟล์ในเครื่อง
4. **กู้ตามลำดับ foreign key** — ใช้ลำดับใน `src/lib/backup-tables.mjs` ตามนั้นเป๊ะ
   (ตารางแม่ก่อนตารางลูก ไม่งั้น insert ตก)
5. **ตรวจก่อนเปิดใช้** — `accounting_integrity()` ต้องไม่มี critical
   และงบทดลองต้องสมดุล ก่อนปล่อยให้ผู้ใช้เขียนข้อมูลใหม่
6. **แจ้งผู้ใช้ตามจริง** — ข้อมูลช่วงไหนหาย เขาต้องคีย์อะไรซ้ำ
   ปิดบังแล้วเขามารู้ทีหลังเสียหายกว่า

## กฎเหล็กระหว่างกู้

- **ห้ามแก้ตัวเลขบัญชีด้วย SQL เพื่อให้ตัวเลขสวย** — ยกเลิก/ออกเอกสารใหม่ผ่านหน้าเว็บเท่านั้น
  ไม่งั้นเอกสารกับสมุดรายวันแยกกันโดยไม่มีร่องรอย (กติกาข้อ 7 ใน CLAUDE.md)
- **โครงสร้างตารางไม่ต้องกู้** — อยู่ใน `supabase/migrations/` ในกิตครบแล้ว
  ข้อมูล JSON + migrations = กู้คืนได้ครบ
- **คีย์ AI/ผู้ให้บริการไม่ได้อยู่ใน bucket โดยเจตนา** — กดออกใหม่จากผู้ให้บริการเสมอ
  (อยู่เฉพาะในไฟล์สำรองในเครื่องเจ้าของ)
