## 0. สรุปให้สั้นที่สุด — ควรทำแบบไหน

**ทำ PWA ให้จบก่อน แล้วค่อยห่อด้วย Capacitor ตอนจำเป็นต้องขึ้นสโตร์จริง ๆ**

เหตุผลที่ชี้ขาด 3 ข้อ:

1. **ระบบนี้เป็น PWA อยู่แล้วประมาณ 80%** — มี `manifest.ts` (standalone · ไอคอน 192/512 ·
   theme สีเขียว) · มี service worker จริงที่ `public/sw.js` และมีโค้ดลงทะเบียนแล้ว
   · Web Push ทำงานได้ (VAPID สร้างเองอัตโนมัติเก็บใน DB) — **เหลือแค่ขัดให้ครบ ไม่ต้องเริ่มใหม่**
2. **Apple เก็บส่วนแบ่ง 15–30% จากการขายในแอป** ซึ่งกินกำไรทั้งหมดของแพ็ก 99–199 บาท
   (ดูข้อ 5.1 — นี่คือจุดเสี่ยงอันดับหนึ่งของโครงการนี้ ไม่ใช่เรื่องเทคนิค)
3. **ระบบบัญชีแก้บ่อยและต้องแก้ให้ถึงมือผู้ใช้ทันที** (กฎภาษีเปลี่ยน · แก้บั๊กตัวเลข)
   เว็บ deploy แล้วถึงทุกคนใน 1 นาที ส่วนแอปสโตร์ต้องรอ review 1–3 วัน **และผู้ใช้ต้องกดอัปเดตเอง**
   ผู้ใช้ที่ไม่อัปเดตจะใช้กฎภาษีเก่าออกเอกสารจริงต่อไป — อันตรายเฉพาะทางของโปรดักต์นี้

**แต่** ถ้าเป้าหมายคือ "มีแอปในสโตร์เพื่อความน่าเชื่อถือตอนขาย" (ซึ่งเป็นเหตุผลทางธุรกิจที่ถูกต้อง
สำหรับลูกค้าไทยกลุ่ม SME) → Capacitor คือทางที่คุ้มที่สุด เพราะใช้โค้ดเว็บเดิมทั้งหมด

## 1. ทางเลือกทั้งหมด เทียบกันตรง ๆ

| | **PWA** (ติดตั้งจากเว็บ) | **Capacitor** (ห่อเว็บเป็นแอป) | **React Native / Expo** (เขียนใหม่) |
|---|---|---|---|
| ใช้โค้ดเดิมได้ | ✅ 100% | ✅ ~95% | ❌ เขียน UI ใหม่ทั้งหมด |
| แรงที่ต้องลง | ~1 สัปดาห์ (ขัดของที่มี) | ~2–4 สัปดาห์ | ~3–6 เดือน |
| อยู่ในสโตร์ | ❌ | ✅ ทั้งสองสโตร์ | ✅ |
| อัปเดตถึงผู้ใช้ | ทันที | ทันที (ส่วนเว็บ) | ต้องรอ review |
| กล้อง/สแกนบิล | ได้ (input capture) | ได้เต็ม (plugin เนทีฟ) | ได้เต็ม |
| Push บน Android | ✅ | ✅ | ✅ |
| Push บน iOS | ⚠️ ต้องติดตั้งลงจอโฮมก่อน | ✅ เต็ม (APNs) | ✅ เต็ม |
| โดนหักส่วนแบ่งสโตร์ | ❌ ไม่โดน | ⚠️ เสี่ยง (ดูข้อ 5.1) | ⚠️ เสี่ยง |
| ค่าใช้จ่ายคงที่ | 0 | Apple $99/ปี + Google $25 ครั้งเดียว | เท่ากัน |
| ความเสี่ยงโดนตีตกตอนส่ง | — | ปานกลาง | ปานกลาง |

**ตัดออกเลย: React Native** — ระบบนี้มี 25+ หน้าหลังล็อกอิน ตารางบัญชี ระบบพิมพ์เอกสาร
รายงานภาษี และตัวแก้เอกสาร การเขียน UI ใหม่ทั้งหมดคือทำโปรดักต์ที่สองขึ้นมาดูแลคู่กัน
ซึ่งจะทำให้ตัวเลขบัญชีสองฝั่งไม่ตรงกันในที่สุด — เป็นความเสี่ยงที่รับไม่ได้กับงานบัญชี

## 3. แผนงาน — เฟสที่ทำได้จริง

### เฟส 1 — ขัด PWA ให้ครบ (~1 สัปดาห์) · ได้ผลทันทีโดยไม่ต้องพึ่งสโตร์

| งาน | ทำไม |
|---|---|
| ตรวจ `public/sw.js` ว่าแคชอะไรบ้าง และ**ห้ามแคชหน้าที่มีตัวเลขบัญชี** | แคชผิด = ผู้ใช้เห็นยอดเก่าแล้วตัดสินใจผิด อันตรายกว่าโหลดช้า |
| ปุ่ม "ติดตั้งลงจอโฮม" ในแอป (จับ `beforeinstallprompt` บน Android) | iOS ไม่มี event นี้ ต้องสอนด้วยภาพ: แชร์ → เพิ่มไปยังหน้าจอโฮม |
| หน้าจอตอนออฟไลน์ที่บอกตรง ๆ ว่าออฟไลน์ | ตอนนี้เน็ตหลุดจะเจอหน้า error ของเบราว์เซอร์ |
| ตรวจ Web Push บน Android จริง + สอน iOS ว่าต้องติดตั้งลงจอโฮมก่อน | iOS ส่ง push ให้ PWA ได้เฉพาะที่ติดตั้งแล้ว |
| ปุ่มถ่ายรูปบิลเรียกกล้องหลังตรง (`capture="environment"`) | ลดจำนวนก้าวของฟีเจอร์ที่ใช้บ่อยที่สุด |

### เฟส 2 — ห่อด้วย Capacitor (~2–4 สัปดาห์) · ทำเมื่อตัดสินใจว่าต้องมีในสโตร์

```
npm i @capacitor/core @capacitor/cli
npx cap init SudoChatBot online.sudochatbot.app
npm i @capacitor/android @capacitor/ios
npx cap add android && npx cap add ios
```

`capacitor.config.ts` แบบที่ใช้ได้กับสถาปัตยกรรมนี้:

```ts
export default {
  appId: "online.sudochatbot.app",
  appName: "SudoChatBot",
  // ⚠️ ชี้ไปเว็บจริง ไม่ bundle หน้าเว็บลงแอป
  // เหตุผล: กฎภาษีเปลี่ยนต้องถึงผู้ใช้ทันที ไม่ใช่รอ review + รอผู้ใช้กดอัปเดต
  server: { url: "https://sudochatbot.online", cleartext: false },
  ios: { contentInset: "always" },
};
```

ปลั๊กอินที่ต้องใช้จริง: `@capacitor/push-notifications` (APNs/FCM) ·
`@capacitor/camera` (ถ่ายบิล) · `@capacitor/filesystem` + `@capacitor/share` (ส่งไฟล์ Excel/PDF
ให้สำนักงานบัญชี) · `@capacitor/browser` (เปิด Stripe **นอกแอป** — ดูข้อ 5.1)

### เฟส 3 — ส่งขึ้นสโตร์

ต้องมีก่อนส่ง: บัญชี Apple Developer ($99/ปี — **ต้องเป็นนิติบุคคลถึงจะใช้ชื่อบริษัทได้**

## 5. 🚨 จุดเสี่ยงที่ต้องระวัง — เรียงตามความเสียหาย

### 5.1 🔴 ส่วนแบ่งสโตร์กินกำไรทั้งก้อน (เสี่ยงสุด และเป็นเรื่องธุรกิจไม่ใช่เทคนิค)

Apple เก็บ 15–30% จากการขาย "digital service" ในแอป และ **บังคับให้ใช้ In-App Purchase**
ถ้าการสมัครนั้นใช้งานในแอปได้ · แพ็กของเราคือ 99–199 บาท/เดือน — โดนหัก 30% แล้ว
เหลือไม่พอค่า AI ที่จ่ายจริงต่อผู้ใช้ด้วยซ้ำ

**ทางออกที่ปลอดภัยที่สุด และเป็นแบบที่ SaaS ส่วนใหญ่ใช้:**
- **ห้ามมีปุ่มสมัคร/จ่ายเงินในแอปเลย** — ในแอปแสดงแค่สถานะแพ็กปัจจุบันและโควตาที่เหลือ
- ผู้ใช้สมัคร/อัปเกรดที่เว็บ (เส้น Stripe เดิมทั้งหมด ไม่ต้องแก้อะไร)
- ถ้าจะมีลิงก์ออกไปเว็บ ต้องตรวจกฎ App Store ฉบับล่าสุดก่อนเสมอ — ข้อนี้ Apple แก้บ่อยมาก
  และต่างกันตามประเทศ **อย่ายึดเอกสารนี้เป็นคำตอบสุดท้าย ให้เปิดกฎจริงตอนจะส่ง**

> เส้นที่ 2 (ลูกค้าของผู้ใช้จ่ายบิลผ่าน PromptPay) **ไม่เข้าข่าย** เพราะเป็นการซื้อขาย
> สินค้า/บริการจริงนอกแอป ซึ่งเป็นข้อยกเว้นที่ชัดเจนทั้งสองสโตร์ — แต่ต้องอธิบายให้
> reviewer เข้าใจตอนส่ง ไม่งั้นมีโอกาสโดนตีตกเพราะเข้าใจผิดว่าเราเลี่ยง IAP

### 5.2 🔴 แคชผิด = ผู้ใช้เห็นตัวเลขบัญชีเก่า

อันตรายเฉพาะทางของโปรดักต์นี้: ถ้า service worker แคชหน้ายอดลูกหนี้/รายงานภาษีไว้
ผู้ใช้จะเห็นเลขเก่าแล้วตัดสินใจ (หรือยื่นภาษี) จากเลขนั้น

**กติกา: ทุกหน้าที่มีตัวเลขเงินหรือภาษี ต้อง network-first เสมอ** แคชได้แค่ไฟล์นิ่ง
(ไอคอน ฟอนต์ CSS/JS) · โหลดช้ากว่าแต่ผิดไม่ได้

### 5.3 🔴 แอปเวอร์ชันเก่าค้างกฎภาษีเก่า

VAT 7% มีวันหมดอายุ และระบบออกแบบให้อัตรามาจากตารางตามวันที่เอกสาร (ไม่ใช่ค่าคงที่ในโค้ด)
ถ้าวันหนึ่งประกาศเปลี่ยน แล้วผู้ใช้ยังใช้แอปเวอร์ชันที่ฝังตรรกะเก่าไว้ = ออกเอกสารผิดกฎหมาย

**ทางออก: ให้แอปเป็นแค่เปลือก ตรรกะภาษีอยู่ที่ server เสมอ** (เป็นเหตุผลที่ `capacitor.config`
ชี้ไป URL จริงแทนการ bundle หน้าเว็บลงแอป) + มีกลไกบังคับเวอร์ชันขั้นต่ำ

### 5.4 🟠 ข้อมูลบัญชีค้างบนเครื่องที่หาย (PDPA)

แอปเก็บ token และอาจแคชข้อมูลลงเครื่อง มือถือหายบ่อยกว่าคอมมาก
- เก็บ token ใน Keychain (iOS) / EncryptedSharedPreferences (Android) เท่านั้น — **ห้าม localStorage**
- มีปุ่ม "ออกจากระบบทุกอุปกรณ์"
- ล็อกแอปด้วยไบโอเมตริกเมื่อเปิดจากพื้นหลัง
- **ห้ามแคชไฟล์เอกสาร/สลิปลงเครื่องถาวร** — ดาวน์โหลดแล้วให้ผู้ใช้จัดการเอง

### 5.5 🟠 โดนตีตกตอนส่งสโตร์

เหตุที่พบบ่อยกับแอปแบบห่อเว็บ:
- **"แอปเป็นแค่เว็บไซต์"** (Apple 4.2 Minimum Functionality) → ต้องใช้ความสามารถของเครื่องจริง
  ให้เห็น: กล้องถ่ายบิล · push · แชร์ไฟล์ · ไบโอเมตริก อย่างน้อย 2–3 อย่าง
- **ลิงก์พาออกไปจ่ายเงินข้างนอก** → ดูข้อ 5.1
- **ไม่มีบัญชีทดสอบให้ reviewer** → ตกทันที
- **ขอสิทธิ์กล้อง/แจ้งเตือนโดยไม่อธิบายเหตุผล** → ต้องเขียน purpose string เป็นภาษาคน
- **ไม่มีวิธีลบบัญชีในแอป** → ทั้งสองสโตร์บังคับ ถ้าแอปสมัครบัญชีได้ต้องลบบัญชีได้ในแอปด้วย
  (เรามีหน้า `/data-deletion` แล้ว แต่ต้องเข้าถึงได้จากในแอป)

### 5.6 🟠 กล้อง OCR บนมือถือจริงต่างจากที่ทดสอบ

บิลไทยส่วนใหญ่เป็นกระดาษความร้อนที่จางแล้ว ถ่ายในร้านแสงน้อย เอียง มีเงามือ
ระบบมีตัวจับผิด OCR อยู่แล้ว (ทานยอดท้ายบิลกับผลรวมที่คำนวณเอง เกิน 5 สตางค์ = เตือน)
**ห้ามตัดตัวจับผิดนี้ออกในแอปเพื่อความลื่น** และควรบังคับความละเอียดขั้นต่ำก่อนส่งขึ้น

### 5.7 🟡 ค่า AI พุ่งเมื่อใช้ง่ายขึ้น

แอปทำให้ถ่ายบิลง่ายขึ้นมาก → จำนวนครั้ง OCR จะพุ่ง และ OCR แพงกว่าแชท ~8 เท่า
เกราะที่มีอยู่แล้ว (`ocrMonthlyGuard` + kill switch + เพดานรายวัน) ต้องถูกเรียกจากเส้นทางแอปด้วย
**ห้ามเปิดเส้นทาง API ใหม่สำหรับแอปที่ข้ามเกราะเหล่านี้** — เคยเกิดมาแล้วกับ
`/api/products/import-extract` ที่เดิมไม่ผ่านทั้ง kill switch และโควตา

### 5.8 🟡 ยังไม่มีไฟล์สำรองออกนอกฐานข้อมูล

ณ วันเขียน ยังไม่ได้ตั้ง `CRON_SECRET` ใน Vercel (มี snapshot รายวันในฐานข้อมูลแล้วจาก
migration 100 แต่ไม่กันกรณีทั้งโปรเจกต์หาย) **มีผู้ใช้จากแอปเพิ่มขึ้นแปลว่าข้อมูลที่เสียหายได้มากขึ้น**
— ต้องปิดข้อนี้ก่อนโปรโมตแอป

## 6. เกณฑ์ตัดสินใจ — ควรลงมือทำแอปเมื่อไหร่

ทำ PWA ให้ครบก่อนเสมอ ส่วนการขึ้นสโตร์ ให้ดูสามข้อนี้:

| ถ้า... | แปลว่า |
|---|---|
| ผู้ใช้ถามหาแอปในสโตร์เองซ้ำ ๆ | ควรทำ — เป็นอุปสรรคการขายจริง |
| ต้องใช้ push บน iOS กับคนที่ไม่ยอมติดตั้ง PWA | ควรทำ — PWA ทำแทนไม่ได้ |
| แค่ "อยากมีแอปให้ดูน่าเชื่อถือ" | ยังไม่ต้องรีบ — เอาเวลาไปปิดเรื่องรับเงินจริงกับไฟล์สำรองก่อน |

**ลำดับที่แนะนำตอนนี้:** ปิด Stripe ให้รับเงินจริงได้ → ตั้ง `CRON_SECRET` →
ขัด PWA ให้ครบ (เฟส 1) → วัดว่ามีคนขอแอปจริงไหม → ค่อยตัดสินใจเฟส 2
